이제 문제 정의서, 관측·행동 계약, 환경 검증, 학습 설정, 평가 보고서, 배포·운영 절차가 준비됐다. 마지막으로 이 문서들이 하나의 과제에서 어떻게 연결되는지 살펴보자. 목표는 가장 높은 점수를 얻은 모델을 소개하는 것이 아니라, **어떤 증거로 무엇을 결정하는지**를 끝까지 추적하는 것이다.

이 글에는 두 종류의 숫자가 등장한다. 첫 번째는 네 lot을 처리하는 작은 결정적 예제로, 아래 코드를 실행해 직접 검산했다. 두 번째는 RL 후보의 학습·평가·운영 판단을 설명하기 위해 만든 **가상 결과**다. 이 글을 위해 실제 RL 모델을 학습하거나 FAB를 운영하지 않았다. 작은 예제의 계산 결과가 RL의 성능을 입증하지도 않는다.

## 1. 과제의 범위를 한 문장으로 고정한다

[[posts/insights/rl-training-and-operations/01-problem-definition|01편]]과 동일하게, 제품 P/Q를 처리하는 설비군 B에서 상위 로직이 지정한 설비에 유효 lot 하나를 선택한다. 투입, route, 납기, 자격, 보전과 타 설비군의 규칙은 고정한다. 모델에 batch 구성이나 의도적 대기 권한을 추가하지 않는다.

업무 목적은 납기 준수율 개선이며, 생산량과 장기 대기는 허용 범위를 정해 함께 본다. 납기 준수율의 분모는 평가 기간에 납기가 도래한 lot 집합이다. 완료된 lot만 분모에 넣지 않고, 기간 말 미완료인 해당 lot도 포함한다. 모델의 reward는 이 업무 목적을 학습에 연결하는 신호이므로 별도 코드로 계산한 KPI와 대조한다.

산출물마다 같은 `problem_version`을 기록한다. 문제 정의서는 lot 선택이라고 쓰고, 환경에서는 모델이 설비 배정까지 바꿀 수 있다면 version 이름만 같아도 실질적으로 다른 과제다. 데이터 hash뿐 아니라 권한과 시간 경계의 의미도 대조해야 한다.

## 2. 네 lot으로 환경과 지표부터 검산한다

전체 FAB를 돌리기 전에 B에 설비 하나만 있는 축소 사례를 만든다. 네 lot은 모두 시각 0에 도착하고 동일하게 처리 가능하며, 초기 setup은 P다. 제품 family가 바뀌면 2시간이 추가되고 처리 중에는 중단하지 않는다. FIFO의 도착 동률은 표의 순서로 해소한다. 고장·이송·추가 도착은 없다.

| lot | family | 처리시간 | 납기 |
|---|---|---:|---:|
| P1 | P | 2시간 | 4시간 |
| P2 | P | 2시간 | 8시간 |
| Q1 | Q | 1시간 | 3시간 |
| Q2 | Q | 1시간 | 10시간 |

FIFO는 `P1 → P2 → Q1 → Q2`, 납기가 빠른 순서인 EDD는 `Q1 → P1 → P2 → Q2`를 선택한다. 이 예제에서는 한 번의 결정이 다음 setup 상태를 바꾸기 때문에, 납기순으로 보낸다는 사실만으로 납기 준수율이 가장 좋아지는 것은 아니다.

| 규칙 | 선택 순서에 따른 완료 시각 | setup 전환 수 | 납기 준수율 | 총 지연시간 |
|---|---|---:|---:|---:|
| FIFO | 2, 4, 7, 8시간 | 1 | 75% | 4시간 |
| EDD | 3, 7, 9, 12시간 | 3 | 25% | 6시간 |

FIFO에서는 Q1만 4시간 늦는다. EDD에서는 Q1이 납기를 지키지만 P1·P2·Q2가 각각 3·1·2시간 늦는다. 이것은 이 작은 조건에서의 규칙 비교이며, FIFO가 일반적으로 EDD보다 좋다는 결론은 아니다.

reward 검산용으로 모든 작업이 완료될 때까지의 비용을 다음처럼 정의해 보자.

$$
R=-\left(\int N(t)\,dt+2\int L(t)\,dt+0.5S\right)
$$

여기서 $N(t)$는 미완료 lot 수, $L(t)$는 납기가 지났으나 미완료인 lot 수, $S$는 setup 전환 수다. 시간 단위는 시간이고 계수는 설명용이다. 비용을 lot·시간 단위로 표현하면 지연 계수 2는 무차원이며, setup 계수 0.5는 전환 한 번을 0.5 lot·시간의 비용으로 환산한다. 모두 시각 0에 도착해 끝까지 추적하므로 첫 적분은 완료 시각의 합, 두 번째 적분은 총 지연시간과 같다. FIFO의 reward는 $-(21+2\times4+0.5)=-29.5$, EDD는 $-(31+2\times6+1.5)=-44.5$다.

이 관계를 확인하면 event마다 비용을 누적하는 코드가 setup 시간을 빼먹거나 완료 시각에 중복 비용을 넣는 오류를 찾을 수 있다. 그러나 이 reward와 납기 준수율은 같은 목적함수가 아니다. 지연 lot의 수를 줄이는 것과 총 지연시간을 줄이는 것은 다른 선택을 유도할 수 있어 실제 학습에서는 별도 KPI 검증이 필요하다.

다음 코드는 위 계산을 재현하는 독립적인 JavaScript 예제다. `handcheck.mjs`에 복사해 `node handcheck.mjs`로 실행할 수 있다. 학습기나 실제 FAB simulator는 포함하지 않는다.

```javascript
const jobs = [
  { id: "P1", family: "P", p: 2, due: 4 },
  { id: "P2", family: "P", p: 2, due: 8 },
  { id: "Q1", family: "Q", p: 1, due: 3 },
  { id: "Q2", family: "Q", p: 1, due: 10 },
]

function evaluate(order) {
  let time = 0, family = "P", setups = 0
  const rows = order.map((job) => {
    if (family !== job.family) {
      time += 2
      setups += 1
    }
    time += job.p
    family = job.family
    return { id: job.id, completion: time, late: Math.max(0, time - job.due) }
  })
  const flow = rows.reduce((sum, row) => sum + row.completion, 0)
  const late = rows.reduce((sum, row) => sum + row.late, 0)
  return {
    rows, setups,
    otd: rows.filter((row) => row.late === 0).length / jobs.length,
    reward: -(flow + 2 * late + 0.5 * setups),
  }
}

console.log(JSON.stringify({
  FIFO: evaluate(jobs),
  EDD: evaluate([...jobs].sort((a, b) => a.due - b.due)),
}, null, 2))
```

이것은 정해진 작업을 모두 처리하는 종료형 사례다. 계속 신규 lot이 들어오는 FAB의 고정 달력 시간 평가를 대체하지 않는다. 손 검산을 통과한 뒤에는 초기 WIP, 고장, 자격, 관측 지연을 포함한 [[posts/insights/rl-training-and-operations/04-environment-validation|환경 검증]]이 별도로 필요하다.

## 3. 작은 검산을 실제 학습 명세로 확장한다

큰 환경에서는 관측을 lot별 예상 처리시간·납기 여유·대기시간과 설비 setup, 제품별 queue 집계로 구성한다고 가정하자. 실제 완료시간과 미래 고장 시각은 입력에서 제외한다. 후보 ID와 mask는 snapshot으로 묶고, 후보가 없으면 모델 대신 기존 대기 경로를 사용한다.

첫 학습 후보는 mask를 지원하는 policy gradient 구현으로 정하되, 구현·reward·전처리 버전을 고정한다. 무엇을 선택했는지보다 선택 근거와 비교 범위가 중요하다. 현행 규칙과 간단한 규칙 조정도 동일한 관측·권한과 평가 조건으로 비교한다. 구체적인 학습 설정 및 복구 규약은 [[posts/insights/rl-training-and-operations/07-training-execution|07편]]의 산출물에 남긴다.

다음 표는 실제 실험 기록을 채울 구조다. ID는 모두 가상 식별자다.

| 문서·파일 | 예시 ID | 다음 단계에서 대조할 항목 |
|---|---|---|
| 문제 정의 | problem-v1 | B의 단일 lot 선택 권한 |
| 입력·행동 계약 | schema-v3 / mask-v2 | 후보 순서, 시각, 단위, 유효성 |
| 환경 검증 | env-v4 / verification-v2 | 검산 결과, 사건 순서, 종료 규칙 |
| 학습 실행 | run-family-B | 설정, training seed, checkpoint·normalizer |
| 모델 선택 | selection-v1 | validation만 사용한 선택 근거 |
| 최종 시험 | test-pack-v1 | 열람 전 고정한 조건과 합격 기준 |
| 배포 후보 | bundle-B | 모델·전처리·guard·fallback의 조합 |

## 4. 첫 실패는 수정 가설을 만드는 데 사용한다

다음은 **가상의 개발 과정**이다. 첫 후보 A는 validation에서 완료 lot의 cycle time을 줄였지만 Q 제품의 미완료 lot age가 증가했다고 하자. “학습이 불안정하다”는 한 문장으로 처리하지 않고 reward 항, 후보 절단, 제품별 선택, 대기열의 변화를 확인한다.

후보 절단 오류가 없고, 긴 대기 lot이 계속 유효 후보에 남아 있었다면 목적 또는 관측의 문제를 조사한다. 이 가상 실패에서는 후보 A의 reward 구현이 앞의 검산식과 달리 완료 lot에만 비용을 부과했다고 가정한다. 미완료 작업의 비용이 누락됐다는 가설을 결과 표만으로 확정하지 않고 작은 통제 사례와 reward 로그로 검증한다.

후보 B는 미완료 lot의 시간 비용을 반영하도록 reward를 수정하고 재학습한 것으로 가정한다. 같은 초기 상태와 외부 사건에서 A·B·현행 규칙을 비교한다. 다른 feature나 학습률까지 동시에 바꾸었다면 그것도 변경 묶음으로 기록하며, reward 하나의 효과라고 주장하지 않는다.

이 과정의 조건은 train 또는 validation 자료다. 최종 test의 실패를 보고 후보 B를 만들었다면 그 test는 이미 개발 자료가 되었으므로, 뒤 단계에는 독립된 최종 시험이 필요하다. 실험 설계와 선택 편향의 원칙은 [[posts/insights/rl-training-and-operations/06-experiment-methodology|06편]]에서 다뤘다.

## 5. 최종 시험은 평균과 허용 조건을 함께 읽는다

validation에서 후보 B를 선택한 뒤 최종 test를 열었다고 가정하자. 아래 표는 **설명을 위해 만든 값이며 측정 결과가 아니다.** 시나리오별 납기 준수율 차이는 baseline 대비 %p, 생산량·age 변화는 baseline 대비 상대 변화율이다.

| 시나리오 | 운영 비중 | 납기 준수율 차이 | 생산량 변화 | Q의 미완료 age p95 변화 |
|---|---:|---:|---:|---:|
| 정상 제품 구성 | 0.6 | +2.8%p | +0.3% | -5% |
| Q 비중 증가 | 0.3 | +2.2%p | -0.5% | +15% |
| B의 일시 고장 | 0.1 | +1.1%p | -0.8% | +8% |

비중은 이 예제에서 사전에 합의한 운영 비중이라고 가정한다. 납기 준수율 개선의 가중 평균은 $0.6\times2.8+0.3\times2.2+0.1\times1.1=2.45$%p다. 하지만 이 값만으로 채택할 수는 없다.

이번 가상 과제에서는 최종 시험 전에 다음 기준을 정했다고 하자.

- 운영 비중으로 집계한 납기 준수율 개선의 신뢰구간 하한이 +2%p를 넘을 것.
- 각 필수 시나리오에서 생산량 감소 1% 이내, 제품별 미완료 age p95 증가 10% 이내를 확인할 것. 추정 불확실성의 처리 방식도 사전 명시할 것.
- 제약과 실행 경로에 대한 별도 검증을 통과할 것.

가중 개선량의 신뢰구간이 **가정상** `[+1.3, +3.6]%p`라면 첫 기준을 통과하지 못한다. 이 구간은 위 세 행만으로 계산한 값이 아니다. 선택한 후보 B의 성능을 판단할 때는 모델을 고정하고 baseline과 공통 평가 경로의 짝을 보존한 원자료 분석이 필요하다. 학습 방법 자체의 성능까지 주장하려면 여러 training seed의 변동과 공통 경로의 의존성도 포함해야 한다. 여러 KPI와 시나리오를 동시에 판단한다면 구간의 동시적 해석과 다중 비교 처리도 평가 계획에 포함한다.

두 번째 기준도 Q 비중 증가 조건의 +15% age 변화 때문에 통과하지 못한다. 추가적인 불확실성 분석이 필요하더라도, 현재 표는 전체 적용을 승인할 충분한 근거가 아니다. 정상 조건만 떼어 제한 적용하려면 그 범위를 탐지하고 유지할 수 있는지까지 포함한 별도 검증이 필요하다.

## 6. 통합 검증을 통과해도 운영 개선이 입증된 것은 아니다

후보 B를 실제 제어에 쓰지 않는 shadow로 연결하면 입력 계약, 추론시간, 최신 상태 재검증과 거절 사유를 점검할 수 있다. 이 작업은 성능 미통과 원인 조사와 별도로 진행할 수 있지만, shadow에서 시스템이 잘 돌아갔다고 test의 성능 기준을 지운 것은 아니다.

또한 timeout이나 후보 초과가 있을 때 fallback이 실행되므로 평가할 대상은 모델 가중치만이 아니다. fallback을 포함한 bundle의 closed-loop 성능을 확인하고, 로그에는 제안한 lot과 실제 실행한 lot을 모두 남긴다. 운영 방식과 평가 방식이 다른 상태로 현장 시험을 시작하지 않는다.

만약 이후 검증된 후보가 배포된다면, 생산량과 납기 cohort의 결과가 확정되는 시차를 고려해 관찰한다. 아직 납기가 도래하지 않은 cohort나 보고가 지연된 자료로 성과를 조기에 확정하지 않는다. 반대로 납기가 지난 미완료 lot은 완료될 때까지 기다리지 않고 납기 미준수로 센다. 경보가 뜨면 모델 재학습, 데이터 수정, 적용 범위 제한 중 어느 조치가 필요한지 [[posts/insights/rl-training-and-operations/11-monitoring-and-retraining|운영 절차]]에 따라 판단한다.

## 7. 최종 의사결정 보고서는 보류도 설명할 수 있어야 한다

위 가상 결과의 결론은 **후보 B의 전체 현장 제어 적용 보류**다. 정상 조건의 평균 개선은 관측할 가치가 있지만, Q 비중 증가 조건의 장기 대기와 최소 개선 기준에 대한 근거가 부족하다. reward를 다시 수정하거나 학습 분포를 넓힐 때는 해당 실패 조건을 개발 자료로 편입하고, 다음 최종 시험을 별도로 설계한다.

보고서에는 다음 다섯 항목을 남긴다.

1. 승인 또는 보류의 대상: 특정 weight가 아니라 범위와 fallback을 포함한 bundle.
2. 통과·미통과 근거: 평균, 구간, 제품별 손실, 실행 경로 검증 결과.
3. 남은 원인 가설: 관측 부족인지 목적 불일치인지 아직 확인되지 않은 부분.
4. 후속 실험: 변경할 요소, 유지할 비교 조건, 필요한 계산 예산.
5. 재검토 조건: 어떤 새 증거가 있어야 다시 적용을 논의할지.

작은 검산은 환경의 오류를 찾고, 학습 실험은 개선 가능한 policy를 찾으며, 최종 평가와 운용 검증은 그 policy를 사용할 조건을 정한다. 이 연결을 문서와 버전으로 남기는 것이 시리즈 전체의 산출물이다. RL을 채택하는 결정뿐 아니라 더 단순한 방법을 유지하거나 적용을 보류하는 결정도 같은 근거 위에서 내려야 한다.
