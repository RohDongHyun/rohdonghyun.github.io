학습 중 reward가 올랐고, 시험용 seed에서도 평균 성능이 좋았다. 그래도 FAB에 배포하기에는 정보가 부족하다. 제품 구성이 바뀌면 어떤가? 병목 설비가 고장 나면 얼마나 빨리 회복하는가? 물량을 많이 처리하는 대신 특정 제품을 계속 뒤로 미루지는 않는가?

강화학습 평가에서 **시나리오**는 policy에 제공하는 초기 상태, 외부 사건, 관측 조건, 실행 조건과 평가 기간을 함께 정한 실험 단위다. 여기서 policy는 관측을 받아 행동을 선택하는 규칙이며, 학습된 신경망도 하나의 policy다. 단순히 난수 seed를 바꾸는 것만으로는 다른 운영 조건을 평가했다고 말하기 어렵다. 이 글에서는 공개 연구가 강조하는 일반화 문제를 출발점으로, 제조 스케줄링에 적용할 평가 설계를 제안한다.

## 시나리오는 여러 축의 조합이다

먼저 정상·비정상을 하나의 목록으로 분류하기보다, 서로 다른 질문을 분리한다. 아래 분류는 특정 논문의 공식 분류가 아니라 평가 누락을 줄이기 위한 설계 틀이다.

| 분류 축 | 시나리오 예 | 확인할 질문과 특징 |
|---|---|---|
| 학습 분포와의 거리 | 익숙한 제품 mix / 신규 mix / 부하 범위 초과 | ID는 학습 분포 안의 새 표본, OOD는 학습 분포 밖의 조건이다. seed가 달라도 조건이 같으면 주로 ID 검증이다. |
| 운영 상태 | 정상 가동 / 수요 급증 / 고장 / 복구 | 평균 효율, 충격 직후 손실, 정상 수준 복귀 시간을 각각 본다. |
| 발생 빈도와 강도 | 일상 변동 / 드문 동시 고장 / 극단적 과부하 | rare는 빈도, stress는 강도에 관한 말이다. 드물지만 약한 사건도 있고 반복되는 강한 부하도 있다. |
| 관측 품질 | 정상 데이터 / 지연 / 누락 / 단위 변경 | 의사결정 능력과 데이터 장애 대응 능력을 구분한다. 물리 상태가 정상이어도 관측은 틀릴 수 있다. |
| 실행 조건 | 즉시 실행 / 지연 / action 거절 | 추론 결과가 현장 상태와 맞지 않을 때의 재검증과 fallback을 평가한다. |
| 시간 구조 | 짧은 과도 구간 / 고정 기간 / 장기 연속 가동 | 초기 상태 의존성, 지연된 손실, 누적 WIP의 영향을 구분한다. |
| 제어 범위 | 단일 설비군 / 여러 설비군 공동 제어 | 국소 개선이 다른 공정의 혼잡으로 옮겨 가는지 확인한다. |

이 표는 가능한 평가 축 전체를 정리한 것이다. 공통 P/Q 사례에서는 설비군 B의 단일 lot 선택 권한을 고정한다. 여러 설비군 공동 제어는 권한을 확장한 별도 과제로 정의해야 하며, 같은 과제의 단순 환경 변화로 비교하지 않는다.

모든 조합을 전수 실행할 필요는 없다. 먼저 정상 조건에서 기준 성능을 측정하고, 한 축씩 바꿔 원인을 파악한 다음, 실제로 함께 일어날 수 있는 복합 조건을 추가한다. 예를 들어 제품 mix 변화와 고장은 각각 통과했어도, 변경된 mix가 특정 설비에 의존하면 두 조건의 결합에서 실패할 수 있다.

학습 환경과 별도의 평가 환경을 두는 이유도 여기에 있다. 반도체 Dispatching을 다룬 Stöckermann 등의 연구도 고장 seed와 load mix를 별개의 불확실성으로 평가한다. 이는 단순한 난수 변경과 운영 조건 변경을 구분해야 한다는 좋은 출발점이다. 다만 이 연구는 산업 데이터에 기반한 시뮬레이션 연구이며, 실제 FAB 배포 성능의 증거로 읽어서는 안 된다. [Stöckermann et al., *Scalability of Reinforcement Learning Methods for Dispatching in Semiconductor Frontend Fabs*](https://arxiv.org/abs/2505.11135)

## 시간의 단위를 먼저 고정한다

Dispatching은 일정한 시간 간격이 아니라 설비 가용이나 작업 완료 사건마다 호출될 수 있다. 따라서 두 policy를 각각 1,000번의 decision으로 비교하면 실제 운영 기간이 달라질 수 있다. 처리 속도가 다른 policy의 같은 step 수는 같은 하루가 아니다.

운영 KPI가 일별 생산량이면 평가도 고정된 달력 시간으로 맞추는 편이 자연스럽다. 초기 상태를 $x_0$, 외부 사건 경로를 $\omega$, 평가 길이를 $H$라 쓰면 결과는 다음과 같이 표현할 수 있다.

$$
Y(\pi;x_0,\omega,H)
$$

여기서 $Y$는 정해진 KPI 하나의 측정값이며, KPI가 여러 개라면 각각 계산한다. 이 식은 성능이 policy $\pi$ 하나의 속성이 아니라는 뜻이다. 같은 policy도 출발 WIP, 고장 시점, 평가 기간에 따라 다른 결과를 낸다. 따라서 결과 표에는 policy 이름만 아니라 이 조건들의 식별자가 필요하다.

장기 정상 상태를 보고 싶다면 초기 상태의 영향을 줄이는 warm-up 구간을 둘 수 있다. 반면 장애 대응 평가에서는 장애 직후의 혼잡과 회복 과정이 관심 대상이므로 이를 warm-up으로 제거하면 안 된다. **warm-up은 초기화 편향을 줄이기 위한 구간이고, recovery는 측정하려는 현상**이다. 자세한 시뮬레이션 출력 분석은 [[posts/foundations/simulation-and-digital-twin/11-output-analysis|출력 분석]]과 연결된다.

가령 정상 상태 평가에는 사전에 정한 warm-up 이후 14일을 관측하고, 장애 평가에는 장애 전 기준 구간부터 복구 후 7일까지 관측할 수 있다. 이 기간은 가상 예시이며 공정의 cycle time과 교대 주기에 맞춰 정해야 한다. 회복 기준도 “괜찮아 보이는 때”가 아니라, WIP가 정한 범위 안에 연속 몇 시간 머무르는지처럼 명시한다. 관측 기간 안에 회복하지 못했다면 미회복으로 기록하며, 그 표본을 평균에서 빼지 않는다.

학습 환경의 episode 종료도 구분해야 한다. 업무상 진짜 종료인 `termination`과 계산 편의를 위해 실행을 끊는 `truncation`은 value target을 구성할 때 의미가 다르다. 외부 시간 제한으로 끊긴 trajectory에서는 적절한 마지막 observation으로 bootstrap해야 한다. 반대로 유한 기한 자체가 문제 정의의 일부라면 남은 시간을 상태에 포함하는 등의 설계가 필요하다. [Gymnasium 공식 문서: Handling Time Limits](https://gymnasium.farama.org/tutorials/gymnasium_basics/handling_time_limits/)

## 평균 점수와 통과 조건을 분리한다

운영에서 자주 발생하는 상황의 기대 성능과 극단적 조건의 안전성은 서로 다른 질문이다. 시나리오 집합을 $S$, 사전에 정한 운영 비중을 $w_s$라 하면 평균 성능은 다음처럼 계산할 수 있다.

$$
J_{\mathrm{op}}(\pi)=\sum_{s\in S}w_s\,\mathbb{E}[Y(\pi;s)],\qquad \sum_{s\in S}w_s=1
$$

이 식의 비중은 실제 운영에서 해당 상황이 차지하는 비율을 표현한다. 신뢰할 근거가 없으면 정확한 기대 운영 성과라고 부르기 어렵다. 평가 데이터에서 모든 시나리오를 같은 횟수로 실행했다고 해서 현실에서도 같은 비중인 것은 아니다.

stress 시나리오를 충분히 실행하되, 운영 평균에는 타당한 비중을 쓰거나 별도 표로 제시한다. 또한 안전 관련 제약은 가중 평균과 별개의 통과 조건으로 둔다. 정상 상황에서 생산량을 크게 올렸다는 이유로 특정 고장 상황의 불법 action을 상쇄해서는 안 된다. 평균, 제품별 성능, 하위 성능 구간, 위반 건수, 미회복 비율을 함께 보면 개선이 어디에서 나왔는지 드러난다.

관측한 위반이 0건이어도 모든 운영 조건에서 위반이 불가능하다고 증명한 것은 아니다. 실행 횟수와 관측 시간 등 노출량, 평가한 조건의 범위를 함께 기록하고, 평가 밖의 조건은 별도 통제 대상으로 남긴다.

## 실행 전에 시나리오 계약을 작성한다

다음은 실제 평가에 쓸 수 있는 계약의 가상 예다. 계약은 데이터 파일 하나보다 넓은 개념으로, 결과 해석에 필요한 조건을 묶은 문서다.

| 항목 | 사전 기록 예 |
|---|---|
| 질문 | 병목 설비 정지 후 납기 준수와 WIP 회복이 기존 규칙보다 나은가 |
| 초기 상태 | 승인된 시점의 WIP snapshot과 설비 상태, snapshot version 고정 |
| 외부 사건 | 외생 주문·고장 경로를 재사용하되, 가동량 의존 고장은 같은 기저 난수와 발생 규칙을 공유 |
| 관측 기간 | 장애 이전 1일과 장애 이후 7일, 장애 이후 warm-up 없음 |
| 비교 대상 | 현재 Dispatching 규칙, 학습 policy, guard 포함 배포 policy |
| KPI | 동일 납기 cohort의 준수율, 시간 평균 WIP, 회복 시간, 제약 위반 |
| 실패 처리 | timeout·비정상 종료를 삭제하지 않고 원인과 미완료 상태 기록 |
| 통과 기준 | 위반 없음, 주요 KPI의 사전 허용 손실 이내, 미회복 조건 별도 확인 |
| 데이터 분리 | 학습·선택에 쓰지 않은 test용 snapshot과 사건 경로 |

held-out 시나리오는 학습과 모델 선택에서 따로 보관한 조건을 뜻한다. test에서 실패한 사례를 보고 reward를 고쳤다면 그 사례는 다음 개발 라운드의 학습 또는 validation 자료가 된다. 같은 사례를 계속 “처음 보는 시험”이라고 부를 수는 없다. 반복 개발을 위해 회귀 검사 집합은 유지하되 최종 판단용 새 holdout을 따로 확보해야 한다.

평가 산출물은 결국 점수 하나가 아니라 **어떤 조건에서 어떤 policy가 허용 가능한가**를 설명하는 표다. [[posts/insights/rl-training-and-operations/02-kpi-and-reward|KPI와 reward]]에서 정한 지표를 어떤 조건에서 측정할지 정했다면, 다음에는 [[posts/insights/rl-training-and-operations/06-experiment-methodology|실험 방법론]]에 따라 비교와 반복, 모델 선택 절차를 설계한다.
